# 词级注音审核设计

## 背景

当前确认页直接编辑歌词处理器生成的内部 token。保存接口又要求行数、token 数量和每个 token 的表面文字逐项不变，因此 Ruby 和对齐所需的细粒度结构会直接暴露给用户。例如内部的 `泣 / き / 声` 会变成三个编辑项，普通假名也曾被完整照抄到页面上。

接口对歌词文字不可修改的限制是必要的，但“人工审核单位必须等于逐字 token”并不是必要条件。更重要的是，任意合法读音不一定存在可靠的逐字切分。例如 `80億分の1 → にこから` 无法推导出每个字符分别对应哪段假名，重复出现的字面假名也可能产生多个同样合法的锚点位置。

本次修改不再强迫系统伪造逐字对应关系。由形态分析和确定性规则生成的审核单位也是发音单位，读音拆出的 mora 才是音频对齐粒度；细分显示只在映射能够被证明唯一时使用。

## 范围

本次只调整注音生成结果进入确认、对齐和 Ruby 显示时的单位：

- 确认页按明确规则生成的审核单位显示；
- 普通假名、标点和空白不生成输入框；
- 保存时只提交实际修改的读音范围；
- 对任意用户读音执行确定性的唯一映射判断；
- 无法唯一映射时保留完整发音单位，不猜测逐字边界；
- 对齐继续使用发音单位中的 mora 时间；
- Ruby 和底部变色明确支持整体回退。

不修改歌词导入、长行拆分、音频识别、时间轴页面或确认页整体布局。

## 发音单位

`LyricToken` 表示一个完整发音单位，而不是一个汉字。它保留：

- `surface`：不可由确认页修改的歌词表记；
- `reading`：完整平假名读音；
- `alignment_pronunciation`：已有的特殊对齐发音；
- 可选的显示映射：能被证明安全时，记录表记范围及其 Ruby 读音；不能安全细分时，记录为整体映射。

例如：

```text
泣き声 / なきごえ
  泣   → な
  き   → 字面假名，不加 Ruby
  声   → ごえ

歌姫 / うたひめ
  歌姫 → うたひめ

80億分の1 / にこから
  80億分の1 → にこから
```

这里的“审核单位”不是对日语中“词”的语言学定义，而是一个可重复执行的产品规则：

- 以 Janome 的词典或形态素单位为基础；
- 只把助动词等活用附属成分并入前面的用言，例如 `隠し + た → 隠した`；
- 确定性数字规则可以把完整数字表达式合并为一个单位；
- FA-Kara 显式标注自身构成一个受保护单位；
- 空格、标点和独立助词形成边界；
- 不因为相邻内容词都含汉字就合并普通句法短语。

因此 `泣き声` 和 `歌姫` 在 Janome 将其识别为一个名词时各自形成一个单位，`強い意志` 则保持 `強い / 意志` 两个单位。旧任务中已经逐字拆分的 token 在进入确认页时会按上述规则组合；无法可靠映射回原 token 边界的部分保守维持原单位。确认后的文档使用发音单位继续后续处理。

## 唯一映射判断

系统只使用字面假名作为硬锚点，不利用“看起来差不多”的读音猜测边界。算法对归一化后的读音枚举所有保持顺序的锚点放置方式，并把合法解数量截断为零、一个或多个：

- 恰好一个合法解：保留该细分映射；
- 没有合法解：整个发音单位作为一个显示范围；
- 存在多个合法解：判定为歧义，整个发音单位作为一个显示范围。

枚举通过动态规划完成，状态只记录“零、一个或至少两个解”，不会因为重复假名数量增加而指数展开。

连续汉字本身不强行逐字分读音。`歌姫 / うたひめ` 即使读音完全正常，也作为一个连续汉字范围显示 Ruby。歧义判断只在一个审核单位内部进行；例如用户把 `思い出 / おもいで` 改为 `思い出 / あいいで` 时，字面 `い` 可落在多个合法位置，系统不采用正则的第一次或最后一次匹配结果，而是整体回退。

显示映射必须满足往返校验：表记范围有序、无重叠且不越界；按映射及字面假名能够精确重建完整表记和完整读音。任何校验失败都改用整体映射。

## 确认数据与保存协议

读取确认页数据时，每行返回服务端生成的审核单位：

```json
{
  "start_token": 2,
  "end_token": 5,
  "surface": "泣き声",
  "reading": "なきごえ"
}
```

`end_token` 为 exclusive 下标。前端不自行猜词界，只保存输入框的初始值与当前值。提交时仅发送真正发生变化的项目：

```json
{
  "corrections": [{
    "line_index": 0,
    "start_token": 2,
    "end_token": 5,
    "surface": "泣き声",
    "current_reading": "なきこえ",
    "corrected_reading": "なきごえ"
  }]
}
```

空修正列表表示接受全部默认读音。后端合并前验证：

- 行号和 token 范围有效、互不重叠；
- `surface` 与 `current_reading` 能由当前 token 精确重建；
- 修正没有改变歌词表面文字；
- 新读音非空且能用于日语 mora 对齐；
- 范围不包含 `alignment_pronunciation` 等不可覆盖信息。

任一修正非法则整次请求失败，原文件和任务状态不变。合法范围被合并为一个发音单位，并根据唯一映射算法生成显示映射。未修改范围的读音和元数据原样保留。

人工确认与 DeepSeek 审阅使用相同的范围验证和合并函数。DeepSeek 额外禁止数字、英文和显式注音修正；人工确认允许用户为这些候选提供作品特有读音。

## 对齐与显示

音频对齐读取发音单位的完整 `reading`，拆成 mora 并保留 mora 时间。它不要求 mora 与表记字符一一对应。

Ruby 优先使用经过校验的显示映射：

- 唯一映射时，只在相应表记范围上方显示读音；
- 整体回退时，把完整读音放在完整发音单位上方；
- 普通假名且读音没有变化时不显示 Ruby。

底部歌词变色遵循相同边界：

- 有唯一映射时，可以按安全的子范围推进；
- 整体回退时，表记作为一个整体变色，不把均分时间伪装成语义对应；
- Ruby 仍可根据已经对齐的 mora 时间逐步变色。

因此系统承诺的是“完整表记与完整读音准确对应”，而不是对任意输入声称已经恢复逐字对应。

## 前端结果

确认页仍显示整行歌词作为上下文，输入项类似：

```text
君           きみ
泣き声       なきごえ
隠した       かくした
歌姫         うたひめ
80億分の1    はちじゅうおくぶんのいち
強い         つよい
意志         いし
```

英文和数字继续使用警示样式。普通假名不提供“显示全部”入口，也不要求用户手动标注读音边界。

## 验证

- 词界：`泣き声`、`歌姫`、带助动词的活用词和完整数字表达式形成预期审核单位；
- 唯一映射：字面假名只有一种位置时生成细分范围；
- 歧义映射：重复锚点、全无锚点、读音与字面假名冲突时整体回退；
- 任意读音：`80億分の1 → にこから` 等修改保持为完整发音单位；
- 保存安全：越界、重叠、表面文字不符、当前读音不符和受保护范围全部原子拒绝；
- 元数据：未修改的 `は → wa` 等特殊对齐信息保持不变；
- 前端：只显示词级审核单位，并只提交实际变化；
- 回归：运行歌词处理、任务生命周期、对齐、Ruby、ASS 和 Kirakara 时间轴测试，确认整体回退不会制造错误的逐字时序。
